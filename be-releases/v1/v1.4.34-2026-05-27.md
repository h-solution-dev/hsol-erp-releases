## v1.4.34 상세

### <span id="karrot-upload-details-조회-메서드-soft-delete-필터-보완">🔧 karrot_upload_details 조회 메서드 soft delete 필터 보완</span>

**설명**
v1.4.33에서 `karrot_upload_details`에 soft delete를 도입하면서 중복 체크 쿼리 3종에만 `deleted_at IS NULL` 조건을 추가했습니다. v1.4.34에서는 QueryBuilder로 작성된 나머지 6개 조회 메서드도 모두 필터링하도록 보완했습니다. 특히 `findRetryTargets`는 매크로 재시도 워커가 사용하는 메서드라서, 사용자가 삭제한 실패 이력을 다시 재시도하던 버그를 방지합니다.

**대상 메서드**
- `checkIfHospitalHasHealthInfoUploadThisMonth` (멱등 체크)
- `findRetryTargets` (재시도 대상 — NOT EXISTS 서브쿼리 포함)
- `findAllByMonth`, `findByHospitalIdAndMonth` (월별 조회)
- `getCompletedUploadsThisMonth` (완료 이력)
- `findUploadDetailsForSummary` (요약 화면)

**영향**
- 매크로 재시도가 삭제된 이력을 다시 시도하지 않음 (의도와 일치)
- 통계/요약 화면이 삭제된 행을 제외하여 정확한 수치 표시

## v1.4.33 상세

### <span id="권한-userrole-root-도입">🔑 권한: UserRole.ROOT 도입</span>

**설명**
시스템 전반의 모든 권한을 가진 최상위 역할 `ROOT`를 추가했습니다. 운영/디버깅/긴급 대응을 위한 슈퍼유저 용도이며, 7개 모든 Guard(RolesGuard, AuthoritiesGuard, SameDepartmentGuard, ExternalRequiresWriterGuard, MarketingTeamGuard, ResponsibilityTypeGuard, AdminOrTeamLeadGuard) 진입부에서 자동 통과되도록 단일 지점에 적용했습니다. 신규 엔드포인트가 추가될 때마다 `@Roles()`에 ROOT를 명시할 필요가 없습니다.

**사용 방법**
1. DB에서 대상 사용자의 `users.role`을 `'root'`로 변경
2. 해당 사용자 재로그인 → 이후 모든 권한 보호 엔드포인트 통과
3. `User.isAdmin` 헬퍼와 boards 컨트롤러 isAdmin 비교 코드도 ROOT 포함하도록 자동 처리

**예제**
관리자 전용 API(`@Roles(UserRole.ADMIN)`)도 ROOT 사용자가 호출하면 200 응답을 반환합니다. SameDepartmentGuard 등 부서 경계 검사도 ROOT는 무시됩니다.

### <span id="당근-업로드-이력-soft-delete">🗑️ 당근: 업로드 이력 soft delete</span>

**설명**
`karrot_upload_details` 테이블에 `deleted_at` 컬럼을 추가하여 soft delete를 지원합니다. 기존에는 "이미 해당 진료일정으로 이번 달 당근 업로드에 성공한 이력이 있습니다." 에러로 같은 블로그 포스트의 재업로드가 차단됐는데, 업로드 이력을 삭제하면 다시 업로드할 수 있습니다. 중복 체크 쿼리 3종(`hasUploadedSourceUrlThisMonth`, `hasUploadedScheduleGuideSourceUrlThisMonth`, `hasUploadedHealthInfoSourceUrlThisMonth`)에 `deleted_at IS NULL` 조건이 추가됐습니다.

**사용 방법**
1. ADMIN/ROOT 권한으로 로그인
2. `DELETE /api/v1/karrot-upload-details/:id` 호출 → 204 No Content
3. 같은 블로그 포스트로 `POST /api/v1/karrot-upload-details/upload-schedule-guide/:blogPostId` 재호출 → 202 Accepted

**예제**
당근 업로드 이력 목록에서 행 우측 삭제 버튼 → 확인 다이얼로그 → DELETE 호출 → 즉시 목록 갱신.

### <span id="당근-pub-karrot-posts-연동-삭제">🔁 당근: pub_karrot_posts 연동 삭제</span>

**설명**
`karrot_upload_details` 삭제 시, 매크로가 함께 생성했던 `pub_karrot_posts`(발행 보고서) 행도 자동으로 soft delete됩니다. 두 테이블은 서로 다른 Aggregate(`karrot/upload-details` 모듈 vs `karrot-posts` 모듈)이므로, 도메인 이벤트(`KarrotUploadDetailDeletedEvent`)를 Outbox 경유로 발행하고 `karrot-posts` 측 핸들러가 수신해서 처리합니다. 매칭 키는 `hospital_id + source_url`(원본 블로그 URL)입니다. 핸들러는 멱등하게 동작하며, 매칭 행이 없으면 그냥 종료합니다.

**예제**
업로드 이력 1건 삭제 → 즉시 `karrot_upload_details.deleted_at` 마킹 → 5초 이내 Outbox relay가 이벤트 발행 → `pub_karrot_posts.deleted_at`도 마킹되어 발행 보고서 화면에서 사라짐.

### <span id="인프라-transactional-outbox-도입">📬 인프라: Transactional Outbox 도입</span>

**설명**
도메인 이벤트의 일관성 보장과 Aggregate 경계 유지를 위해 Transactional Outbox 패턴을 신규 도입했습니다. Application Service에서 Aggregate 변경 + `outbox_messages` 행 INSERT를 하나의 DB 트랜잭션으로 commit하고, 별도 워커(`OutboxRelayWorker`, `@Cron('*/5 * * * * *')`)가 PENDING 메시지를 폴링해 NestJS `EventBus`로 발행합니다. 이벤트 핸들러는 자기 모듈의 Aggregate만 변경하여 DDD Aggregate 경계를 유지합니다. 향후 도메인 이벤트는 이 경로를 표준으로 사용합니다.

**구성 요소**
- `OutboxPublisher` — Application Service에서 `publishInTransaction(input, manager)` 호출
- `OutboxEventRegistry` — 각 모듈이 자기 이벤트 타입과 deserializer 등록
- `OutboxRelayWorker` — 5초 주기 폴링, BATCH_SIZE=50, MAX_RETRY=5, 단일 인스턴스 가정 (running 플래그로 중복 실행 방지)
- `outbox_messages` 테이블 — `(status, occurred_at)` 인덱스

**예제**
karrot 업로드 이력 삭제가 첫 적용 사례입니다. 단일 DB·단일 앱 환경에서도 향후 외부 시스템 연동 시 그대로 통합니다.

### <span id="인증-jwt-만료-연장">🔐 인증: JWT 만료 연장</span>

**설명**
Access Token 만료를 15분 → 7일, Refresh Token 만료를 7일 → 30일로 연장했습니다. 사용자가 자주 재로그인해야 하는 불편을 줄이기 위한 변경입니다. 7일 이내에 한 번이라도 API를 호출하면 Refresh로 자동 갱신되어 사실상 30일간 로그인 유지됩니다.

**보안 영향**
- Access Token 탈취 시 즉시 무효화 어려움 (서버 DB에 저장되지 않음)
- 운영자 명령으로 강제 로그아웃이 필요하면 `JWT_SECRET` 변경(전체 토큰 무효화) 또는 사용자 단위 블랙리스트 도입 필요

병원 상세조회(`findDetailWithRelations`)가 11개 LEFT JOIN을 단일 쿼리로 실행하여 카테시안 곱이 발생하던 문제를 해결했습니다. 4개의 독립 OneToMany 관계를 `Promise.all` 병렬 쿼리로 분리하여 전송 데이터량을 약 1/30로 줄였습니다. 응답 형태는 기존과 동일합니다.

**설명**
당근 자동화 스크린샷 캡쳐 시 하얀 화면이 나오던 문제를 수정했습니다. `[data-part="paper"]` 컨테이너만 확인하고 바로 캡쳐하던 방식에서, 내부 텍스트(`.post-content-renderer-text`) + 이미지 로드 완료 + 페인트 사이클(`requestAnimationFrame` 2회)을 확인한 후 캡쳐하도록 변경했습니다. 스크롤 후에도 페인트 완료를 대기합니다.

### <span id="db-pub-테이블-soft-delete-url-충돌-해결">🗄️ DB: pub 테이블 soft-delete URL 충돌 해결</span>

**설명**
10개 pub 테이블에서 소프트 딜리트 후 같은 URL로 재등록 시 UNIQUE 제약 위반이 발생하던 문제를 해결했습니다. MariaDB 가상 컬럼(`active_url`)을 추가하여 활성 레코드만 URL unique를 보장하고, 삭제된 레코드의 URL 데이터는 그대로 보존됩니다.

**대상 테이블**
pub_knowledge_in_posts, pub_news_article_posts, pub_hidoc_posts, pub_cafe_posts, pub_cafe_comment_reports, pub_experience_reports, pub_instagram_card_news, pub_instagram_reels, pub_karrot_posts, pub_naver_blog_posts

**배포 시 필수**
`npm run migration:run` 실행 필요 (`ReplaceUrlUniqueWithActiveUrl` 마이그레이션)
